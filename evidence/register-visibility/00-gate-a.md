# C1 语体可见性 —— 验收材料

日期：2026-08-10 · 分支 `codex/m2-stable-roles` · 设计：`docs/PROJECT.md` §5.6（另更新 §11.7）

## 1. 先查真实数据，范围因此收窄了

原提案是「每条纠错都给 2–3 个版本并标注语体」。查完真实库后**这个提案被数据否掉了**：

**① §11.7 自己的触发条件没有满足。** 它写的是「若实际使用中出现过*同一句、不同角度*给出语体不一致的例句」。真实库里四个角度总共只用过 5 次：

```
   lens    | count
 structure |     2
 chinese   |     2
 meaning   |     1
```

**没有任何一句被两个角度问过**，所以那个现象根本没发生。§11.7 的规则是「在真的撞见之前不预先加约束——提示词每多一条，模型遵守其余各条的概率就低一点」，因此 `lenses.py` 一个字没改。

**② 但纠错这一侧撞见了一次。** 14 条真实纠错里 1 条：

> 用户原话：話したいことが**話さない**（全句简体）
> 改写：話したいことが**話せません**（丁寧体）
> reason_zh / summary_zh：只解释可能形，**一个字没提语体也被换掉了**

**③ 顺带发现一个明确缺陷。** 有一条 `replacement` 与原文完全相同：

```
 id | category | original_fragment | replacement
  2 | register | 日本人として      | 日本人として
```

它的 `reason_zh` 自己说「这个表现本身没问题」。界面上就是一张「把 X 改成 X」的卡片。

**所以做的是窄版**：14 条里真有语体问题的只有 1 条，其余大多是纯语法（て形拨音便、い形过去），给三档语体是纯噪音。

## 2. 改了什么

| 层 | 内容 |
|---|---|
| 校验 | `CorrectionOutput` 过滤 `original == replacement` 的 item。**全部为无效时降级为 `needed=False`，不抛错**（§12.5：模型的毛病该由它自己承担，不该连累使用者这一轮） |
| 校验 | `CorrectionItemOutput.same_register_replacement`，等于 `replacement` 或空白时丢弃（没有信息量） |
| 提示词 | 两条：不许发出无变化的 item；语体若被改动必须点明并给同语体版本，**但语体变化本身就是纠错目的时不给** |
| 数据 | `chat_correction_item` 加 `same_register_replacement TEXT`（`ADD COLUMN IF NOT EXISTS`，按 §7.5 留在基线） |
| iOS | 纠错卡在 `原文 → 改写` 下面多一行「保持你原来的语体：…」，**正文级字号**（§1.5：该读的内容不能用最小最淡的字） |

**为什么无效 item 靠校验而不只靠提示词**：沿用 §12.5 的先例——服务端只接受它能验证的，其余一律丢弃。提示词也写了，给模型一个做对的机会，但不依赖它。

## 3. 真实模型验证（连百炼 `qwen3.7-max`）

### 3.1 那句实际出过问题的话

输入：`話したいことが話さない`

```
整句改写: 話したいことが話せない
        話さない → 話せない
   同语体版本: None
       类别: grammar
       理由: 「話さない」表示主观上选择不说，而这里想表达的是"无法说出"的状态，
             应使用可能形的否定「話せない」。中文母语者容易把"不会/不能"和"不做"
             混淆，需注意日语中可能性与意志的区分。
```

**结果比设计预期更好。** 之前它返回丁寧体「話せません」并且不说明；现在它**根本不再切换语体了**，返回保持简体的「話せない」。`same_register_replacement` 为 null 是**正确的**——语体压根没动。

也就是说这条规则的主要效果不是「切换后解释」，而是**让它停止了不必要的切换**。那个字段因此主要是安全网。

### 3.2 语体变化本身就是纠错目的的情况

这是我在实测中才想到的反例：如果对上司说简体，"保持你原来的语体"是**错的建议**。

输入（话题：和公司的部长汇报工作）：`部長、明日休む`

```
整句改写: 部長、明日お休みをいただきます。
        明日休む → 明日お休みをいただきます
   同语体版本: None          ← 正确，没有给
       类别: register
       理由: 对上级说「休む」是命令或宣告语气，非常失礼。应使用谦让表达
             「お休みをいただく」来表示请求许可，这是职场请假的标准说法。
```

模型自己判断对了，但那是靠判断不是靠规则，所以**已把这一条写进提示词**（`category=register` 时不给该字段）。

## 5. 偏离说明

**范围比原提案窄，且是数据要求的。** 详见第 1 节。原提案「每条都给 2–3 个版本」会给 13/14 条纠错添加无用的语体对照，并正面撞上 §11.7 关于提示词膨胀的警告。已在提问后由使用者确认走窄版。

**§11.7 没有关闭。** 角度那一侧的现象仍未观测到（角度只用过 5 次、无同句多角度）。纠错侧的这一次不算它写的触发条件，因此 §11.7 保留并补记了这次复查结论。

## 6. 一个连跑两次才暴露的教训（§11.6 的实例）

第一次跑全量时出现 **2 failed**，两次都一样，失败在两条**既有**测试上：

```
assert repository.chat_corrections(category="register") == []   → 实际有一条
assert reordered[0][0] == priority_key                          → 语法目录排序被影响
```

原因是我**用同一个数据库既跑真实模型实验、又跑测试套件**——上面 3.2 那条 `register` 类纠错留在库里，而这两条既有测试假设库里没有别的数据。

换全新库后 229 全通过。**这不是既有测试的问题，是我的操作问题**：§11.6 记着「集成测试之间存在状态泄漏」，而这次证明**真实链路验证也必须和测试套件分库**，否则「连跑两次」这道闸会被自己的验证数据打红。已把这条写进本材料，`harvest_c1_test`（被污染的那个）保留未删以备复查。
